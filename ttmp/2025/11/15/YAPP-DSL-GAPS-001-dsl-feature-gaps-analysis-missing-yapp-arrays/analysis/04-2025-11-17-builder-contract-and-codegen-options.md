## Scope

Analyze current use of `[]map[string]any` (inputs) and `[][]any` (outputs) across builders/emitters, how code generation participates today, and options to strengthen contracts between validation, building, and SCAD emission. Includes pros/cons, codegen implications, and migration paths.

## Pain points

- Weak input type contract:
  - Builders accept `[]map[string]any` requiring every module to decode and validate again, often via YAML re-marshal/unmarshal.
  - The model also stores untyped maps, so the lack of typing propagates.

- Weak output shape:
  - `[][]any` allows accidental insertion of unsupported values at runtime (only caught by SCAD writer).
  - Special-cases (e.g., cutouts producing multiple arrays) require ad hoc handling in `features.go`.

- Codegen gap:
  - Codegen does not generate builders or typed adapters, only structs, structure validators, tests, and registration.
  - No standardized typed “IR” for SCAD arrays.

## Design options to strengthen the contract

### Option A — Typed inputs to builders via generated decode (least invasive)

- Change module builders to accept typed items (`[]<Module>Item`) instead of `[]map[string]any`.
- Provide, via schemagen, a generated `Decode(items []map[string]any) ([]<Module>Item, error)` function per module to convert validated maps to typed items without YAML roundtrip (fast path with explicit casts).
- Add a small generated wrapper per module that implements registry `Build([]map[string]any) ([][]any, error)` by calling `Decode` then the typed builder.

Pros:
- Keeps registry and emission unchanged (minimal blast radius).
- Removes YAML re-marshal/unmarshal, improves performance and errors.
- Strong typing inside builders; better editor support and compile-time checks.

Cons:
- Output still `[][]any`.
- Cutouts still special-cased for output shape.

Codegen changes:
- Generate per-module `Decode` and `AdapterBuild` wrappers.
- Optionally generate a typed builder signature stub to encourage usage.

### Option B — Introduce a SCAD IR (ArrayDecl) for outputs

- Define a typed IR for outputs, e.g.:
  - `type ArrayDecl struct { Name string; Rows [][]any }`
  - Or stricter: `type Value interface{ write(*strings.Builder) }` with constructors for numbers, strings, `scad.Raw`, lists, and `scad.Undef`.
- Change builders to return `[]ArrayDecl` (zero, one, or many arrays).
  - Normal modules return one decl `[{Name: "pushButtons", Rows: ...}]`.
  - Cutouts return six decls (one per face) directly—no special-case in `features.go`.
- Update emission to iterate `[]ArrayDecl` and call an IR-aware writer.

Pros:
- Eliminates `features.go` special-casing for multi-array outputs.
- Aligns all modules behind a unified “emit arrays” contract.
- Paves the way to add validation hooks for rows and values.

Cons:
- Requires changing the generator and possibly registry interface or adding an adapter layer.
- Still permits `any` unless we also strengthen the row element type.

Codegen changes:
- Generate module wrappers that return `[]ArrayDecl` from builders.
- Generate the trivial emit loop for array modules (could even be per-module).

### Option C — Typed Model storage + typed FeatureModule interface (bigger)

- Store typed items in `Model` fields, e.g., `PcbStands []pcbstands.PcbStandsItem` instead of `[]map[string]any`.
- Update `collectFeatureModules` to use generated `Decode` during collection, not in the builder.
- Change `arrayFeatureModule` builder signature to accept typed slices.

Pros:
- Removes untyped maps from the hot path entirely after resolution.
- Builders simplify (no decode step).

Cons:
- Larger surface change (model, collectors, feature wiring).
- Heterogeneous typed slices complicate generic interfaces; would need generated per-module collector glue or use `any` internally but typed at edges.

Codegen changes:
- Generate collectors that decode into typed slices and store in the model.
- Optionally generate model field types per module (bigger refactor).

### Option D — Capability-based module interfaces (extensible shape)

- Keep a minimal registry interface but allow optional capabilities via type assertions:
  - `type FacePartitioned interface { BuildByFace([]<Item>) (map[string][][]any, error) }`
  - `type ArrayEmitter interface { BuildArrays([]<Item>) ([]ArrayDecl, error) }`
- `features.go` checks capabilities and routes accordingly; default path remains arrays.

Pros:
- Makes special output shapes explicit in types.
- Avoids one-off hacks (like cutouts stub `Build`).

Cons:
- More interfaces to maintain; still need typed items for best effect.

Codegen changes:
- Emit capability implementations based on schema metadata (e.g., an optional `output_kind: multi_array_by_face`).

### Option E — Strongly typed SCAD values (optional)

- Replace `any` in rows with a constrained value type, e.g.:
  - `type Value interface{ isSCADValue() }` with implementations `Number`, `Raw`, `String`, `List`, `Undef`.
- Writer only accepts these values; builders must construct them via helpers.

Pros:
- Compile-time guarantee that builders cannot insert unsupported types.

Cons:
- Heavier change across all builders and tests; ergonomics cost.

Codegen changes:
- Provide helper constructors for common patterns, generate stubs using them.

## Codegen levers we can add now

1) Per-module Decode (A)
- Generate `Decode([]map[string]any) ([]<Item>, error)` using the schema field metadata and the structure validator’s knowledge of item shapes.
- Builders become typed: `BuildTyped([]<Item>) (...)`.
- Generate `NewModule()` and wrapper `Build` that calls `Decode` then `BuildTyped`.

2) Output kind metadata
- Accept a schema-level key (non-breaking), e.g.:
  - `output: array` (default)
  - `output: multi_array_by_face`
  - `output: custom` (no generic wrapper)
- Generate the appropriate module wrapper and, for array outputs, a simple `Emit` adapter that converts to `ArrayDecl` or calls `writeArrayDecl` directly.

3) ArrayDecl IR (B)
- Introduce a small IR and make the codegen wrapper return `[]ArrayDecl`.
- Update `emitFeatureModules` to gather decls from all modules and emit in order (with optional deterministic ordering).

4) Optional: Generate FieldSpec for help/docs
- Implement `Fields()` from schema (currently TODO in many modules) for better introspection.

## Migration paths

- Path 1 (low risk): A → B
  - Phase 1: Generate Decode + typed builder stubs; keep rows `[][]any`. Builders become typed immediately; performance and safety improve.
  - Phase 2: Introduce `ArrayDecl` IR and update emission. Cutouts lose special-case.

- Path 2 (broader): A → C (+D optional)
  - Phase 1: As above (Decode + typed builders).
  - Phase 2: Store typed slices in `Model`, generate typed collectors, and adjust `arrayFeatureModule` to accept typed builders.
  - Optional: Add capability interface for multi-array outputs instead of hardcoding cutouts.

## Recommendation

Short term:
- Implement Option A via codegen:
  - Generate `Decode` per module and a wrapper for `Build([]map[string]any)` that calls typed `Build`.
  - Update existing builders to accept typed items.
  - Net effect: remove YAML marshal/unmarshal, reduce runtime surprises, keep emission unchanged.

Medium term:
- Implement Option B (ArrayDecl IR) and change emission to a unified “module returns arrays to emit” flow. Use schema `output` metadata to generate wrappers and remove `cutoutFeatureModule` special casing.

Longer term:
- Consider Option C (typed Model storage) if we want end-to-end type safety after resolution, plus Option D if we foresee additional non-array outputs.

## Risk/Impact summary

- A: Localized, no behavior change, immediate dev ergonomics and perf wins.
- B: Moderate; central emission change, simpler module authorship; removes special-case.
- C: Larger; model and collectors change; highest type-safety payoff.
- D: Incremental; improves clarity for special outputs without forcing B/C.
- E: Optional; compile-time safety for SCAD values at cost of ergonomics.
