# Debate Round 5: Validation - When and How Do We Validate?

## Question

Should composite-generated DSL be validated before merging, after merging, or both? How do we ensure generated DSL is valid?

## Primary Candidates

- `pkg/resolver/resolver.go` "The Expression Evaluator" (handles validation)
- Dr. Sarah "The Architect" Martinez (wants early validation)
- Jordan "The Module Author" Kim (wants clear error messages)
- `go.mod` "The Dependency Manager" (cares about type safety)

---

## Pre-Debate Research

### Research 1: Current Validation Flow

**From `pkg/resolver/validation.go` and `pkg/resolver/resolver.go`:**

**Validation happens in 2 phases:**

**Phase 1: Structure Validation (before resolution)**
```go
// In ResolveResult(), line 47-50
if err := validateStructure(state); err != nil {
    return nil, errors.Wrap(err, "structure validation")
}
```

**What it checks:**
- Field types (string vs number)
- Required fields present
- Array vs map structure
- Schema compliance

**Phase 2: Constraint Validation (after resolution)**
```go
// In ResolveResult(), line 93-96
if err := validateConstraints(state); err != nil {
    return nil, errors.Wrap(err, "constraint validation")
}
```

**What it checks:**
- Enum values (shape: "rectangle" vs "oval")
- Min/max constraints
- Cross-field dependencies
- Numeric ranges

### Research 2: Validation Implementation

**From `pkg/resolver/validation.go`:**

```go
func validateStructure(doc map[string]any) error {
    features, ok := doc["features"].(map[string]any)
    if !ok || features == nil {
        return nil
    }
    
    for key, value := range features {
        path := "features." + key
        module, found := registry.Get(path)
        if !found {
            continue // Unknown module - skip
        }
        
        schema := module.Schema()
        if err := schema.ValidateStructure(path, value); err != nil {
            return errors.Wrapf(err, "validate %s", path)
        }
    }
    
    return nil
}
```

**Key Finding:** Validation loops through `features.*` and calls module schema validators.

**Implication:** If composite modules generate `features.cutouts` entries, they'll be validated by `cutouts.Schema().ValidateStructure()`.

**This is automatic if we use Hook A (before resolver).**

---

### Research 3: Validation Timing Options

**Option 1: Validate After Merge (Hook A)**
```
Input YAML → Composite Transform → Merged YAML → Validate → Resolve → ...
```

**Pros:**
- Composite-generated DSL validated by regular module validators
- No duplicate validation logic
- Errors caught early

**Cons:**
- If composite generates invalid DSL, error message points to merged DSL (not composite module)
- Harder to attribute errors

---

**Option 2: Validate Before Merge**
```
Input YAML → Composite Transform (with validation) → Merge → Validate → Resolve → ...
```

**Pros:**
- Composite modules validate their own output
- Clear error attribution ("lcd module generated invalid cutout")
- Fail immediately if composite is buggy

**Cons:**
- Duplicate validation logic (composite validates, then resolver validates)
- More complex composite module implementation

---

**Option 3: Trust Composite Modules (No Pre-Merge Validation)**
```
Input YAML → Composite Transform (no validation) → Merge → Validate → Resolve → ...
```

**Pros:**
- Simple composite modules (no validation logic)
- Single validation pass (after merge)
- Less code duplication

**Cons:**
- If composite generates invalid DSL, caught late
- Error messages less clear (blame merged DSL, not composite)

---

### Research 4: Error Message Analysis

**Scenario: LCD module generates invalid cutout (missing required field)**

**With Option 1 (validate after merge):**
```
Error: validate features.cutouts: features.cutouts[2].shape: required field missing
```

**User sees:** Error in cutouts array, entry 2.

**Problem:** Entry 2 was generated by lcd module, but error points to cutouts.

**User confusion:** "I didn't define cutouts[2]!"

---

**With Option 2 (validate before merge):**
```
Error: composite module 'lcd': generated invalid cutout: shape field required
```

**User sees:** Error in lcd module.

**Problem:** User needs to understand lcd module internals to fix.

---

**With Option 3 (trust composite):**
Same as Option 1.

### Dr. Sarah "The Architect" Martinez

*[Reviews validation architecture, error handling]*

Resolver raises a critical point: **error attribution**.

**The question is:** Who's responsible for validation?

**Option A: Composite modules validate themselves (Option 2)**
- Composite module generates DSL
- Composite module validates DSL (calls schema validators)
- If invalid, error says "lcd module generated invalid..."
- **Clear attribution** ✅

**Option B: Resolver validates everything (Option 1/3)**
- Composite module generates DSL (no validation)
- Resolver validates merged DSL
- If invalid, error says "features.cutouts[2]..."
- **Unclear attribution** ❌

**From an architecture perspective: Composite modules should validate their output.**

**This follows the "generate and validate" pattern:**
- Module generates DSL
- Module ensures DSL is valid
- Downstream systems trust the DSL

**Compare to regular modules:**
- Regular modules have `Build()` function
- `Build()` validates during construction (e.g., checking shape enums)
- Downstream emission trusts Build() output

**Composite modules should be the same:**
- `Transform()` generates DSL
- `Transform()` validates generated DSL
- Downstream resolver trusts the DSL

**My position: Option 2 (validate before merge).**

Composite modules validate their own output for clear error attribution.

### `go.mod` - "The Dependency Manager"

*[Analyzes type safety, validation guarantees]*

I care about **correctness**. Let me analyze the safety of each option.

**Option 1 (validate after merge):**
- Composite generates DSL (might be invalid)
- Merge (might create inconsistent state)
- Validate (catches errors, but late)
- **Safety: Medium** ⚠️

**Option 2 (validate before merge):**
- Composite generates DSL
- **Validate immediately** (catch errors early)
- Merge (guaranteed valid)
- Validate merged (double-check)
- **Safety: High** ✅

**Option 3 (trust composite):**
- Composite generates DSL (might be invalid)
- Merge (might be invalid)
- Validate (catches errors)
- **Safety: Medium** ⚠️

**Option 2 provides strongest guarantees.**

**But here's a question:** Do we validate **before merge** AND **after merge**?

**Before merge:**
- Validate each generated entry independently
- Catch malformed entries

**After merge:**
- Validate merged array
- Catch inter-entry conflicts (overlaps, duplicates, etc.)

**I think: Both.**

**Validation should happen at both levels:**
1. **Composite modules validate their output** (before merge)
2. **Resolver validates merged DSL** (after merge)

**This provides defense in depth.**

**My position: Double validation (Option 2 + standard validation).**

Safety over convenience.

Jordan, it's not paranoid. It's **defense in depth**.

**What if:**
- Composite module has a bug
- Validation is incomplete
- Edge case slips through

**If we validate again after merge:**
- Catch the bug
- Prevent invalid SCAD generation
- **Safety net** ✅

**The cost:** ~5ms extra validation time.
**The benefit:** Catch bugs that slip through composite validation.

**Single-entry validation misses this.** Merged validation catches it.

**Double validation is not redundant.** It's layered safety.

**PRO Option 1 + Provenance (Validate After Merge):**
1. **Simple composite modules** - No validation logic needed
2. **Single validation pass** - No duplication
3. **Clear errors** - Provenance shows source
4. **Reuses existing validators** - No new validation code

3. **Explicit** - Composite modules own their validation

**CON Option 3 (Trust Composite):**
- Unclear error messages
- Late error detection
- No safety net

### Validation Flow Finalized

```
1. Parse Input YAML
2. Composite Transform (generate DSL)
   - No validation here
   - Just generate entries
3. Merge with Provenance Tracking
   - Record: "features.cutouts[2] from lcd module"
4. Validate Structure (Phase 1)
   - Check all entries (user + composite)
   - Error messages show provenance
5. Resolve Expressions
6. Validate Constraints (Phase 2)
7. BuildModel
8. EmitSCAD
```

### Open Questions Resolved

- ✅ **Validate after merge** (Option 1)
- ✅ **Track provenance** for error attribution
- ✅ **Single validation pass** (no duplication)
- ✅ **Reuse existing validators** (no new validation code in composites)
- ✅ **Clear error messages** (show source module)

### Validation Responsibilities

**Composite Modules:**
- Generate DSL entries
- **Do NOT validate** (keep simple)
- Trust downstream validation

**Resolver:**
- Validate all DSL (user + composite)
- Show provenance in errors
- Single source of truth for validation

**Clean separation of concerns.**
