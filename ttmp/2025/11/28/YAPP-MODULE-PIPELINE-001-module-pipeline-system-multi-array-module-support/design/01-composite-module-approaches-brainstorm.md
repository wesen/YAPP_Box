# Composite Module Approaches - Brainstorming Multiple Architectures

## Overview

This document explores multiple architectural approaches for supporting composite modules (e.g., LCD module that adds cutouts + mounting holes). The focus is on **DSL-level transformations** rather than modifying the existing module system, as suggested by the user.

## Design Goals

1. **Minimal disruption** to existing module system
2. **Separation of concerns** - composite modules don't interfere with existing modules
3. **Clear boundaries** - easy to understand what composite modules do
4. **Maintainability** - changes don't cascade through existing code
5. **Extensibility** - easy to add new composite modules

## Approach 1: Pre-Processing DSL Transformation

### Concept

Composite modules act as **DSL transformers** that modify the input YAML before it reaches the existing module system.

### Architecture

```
Input YAML
    ↓
[Composite Module Pipeline]
    ↓ (transforms YAML)
Transformed YAML
    ↓
[Existing Module System]
    ↓
SCAD Output
```

### Implementation Flow

1. **Parse Input YAML** → `input.yaml`
2. **Detect Composite Modules** → Find `features.lcd`, `features.sensor_module`, etc.
3. **Execute Composite Modules** → Each module reads its DSL entry and generates additional DSL entries
4. **Merge Transformations** → Combine original YAML with generated entries
5. **Continue Normal Pipeline** → Pass merged YAML to existing resolver/module system

### Example: LCD Module

**Input DSL:**
```yaml
features:
  lcd:
    - display:
        face: front
        position: [50, 30]
        size: [80, 40]
      mounting:
        type: pcb_stands
        positions: [[45, 25], [45, 55], [105, 25], [105, 55]]
        standoff_height: 5
        diameter: 3
```

**Composite Module Transforms To:**
```yaml
features:
  lcd:
    - display:
        face: front
        position: [50, 30]
        size: [80, 40]
      mounting:
        type: pcb_stands
        positions: [[45, 25], [45, 55], [105, 25], [105, 55]]
        standoff_height: 5
        diameter: 3
  
  # Generated by lcd module:
  cutouts:
    - face: front
      from_face_left: 50
      from_face_bottom: 30
      width: 80
      length: 40
      shape: rectangle
  
  # Generated by lcd module:
  pcb_stands:
    - x: 45
      y: 25
      height: 5
      diameter: 3
    - x: 45
      y: 55
      height: 5
      diameter: 3
    - x: 105
      y: 25
      height: 5
      diameter: 3
    - x: 105
      y: 55
      height: 5
      diameter: 3
```

### Implementation Details

**New Component: `pkg/composite/`**

```go
// CompositeModule defines a DSL transformer
type CompositeModule interface {
    // Name returns the module identifier (e.g., "lcd")
    Name() string
    
    // Path returns the DSL path (e.g., "features.lcd")
    Path() string
    
    // Transform reads the module's DSL entry and generates additional DSL entries
    Transform(ctx context.Context, moduleData map[string]any, resolved map[string]any) ([]DSLEntry, error)
}

// DSLEntry represents a generated DSL entry to merge
type DSLEntry struct {
    Path  string      // e.g., "features.cutouts"
    Value interface{} // Array or map to merge
    Merge MergeStrategy
}

type MergeStrategy string

const (
    MergeAppend MergeStrategy = "append"  // Append to existing array
    MergeReplace MergeStrategy = "replace" // Replace existing value
    MergeMerge   MergeStrategy = "merge"   // Deep merge maps
)
```

**Pipeline Integration:**

```go
// In pkg/resolver/resolver.go or new pkg/composite/pipeline.go
func ProcessCompositeModules(input map[string]any, resolved map[string]any) (map[string]any, error) {
    result := deepCopy(input) // Start with original
    
    // Find all composite module entries
    features, _ := getMap(input, "features")
    for key, value := range features {
        module := compositeRegistry.Get(key)
        if module == nil {
            continue // Not a composite module
        }
        
        // Transform
        entries, err := module.Transform(ctx, value, resolved)
        if err != nil {
            return nil, err
        }
        
        // Merge generated entries
        for _, entry := range entries {
            result = mergeDSLEntry(result, entry)
        }
    }
    
    return result, nil
}
```

### Pros

✅ **Clean separation** - Composite modules don't touch existing module system
✅ **Easy to understand** - DSL transformation is explicit and visible
✅ **Debuggable** - Can inspect transformed YAML before processing
✅ **No changes to existing modules** - Zero impact on current system
✅ **Flexible** - Can generate any DSL structure
✅ **Testable** - Can test transformations independently

### Cons

❌ **DSL manipulation complexity** - Need robust YAML merging logic
❌ **Ordering matters** - Composite modules must run before regular modules
❌ **Potential conflicts** - Generated entries might conflict with user entries
❌ **Validation complexity** - Need to validate merged DSL
❌ **Error handling** - Errors from composite modules happen before regular validation

### Implementation Complexity

- **Medium** - Need new composite module system, DSL merging logic, pipeline integration
- **Estimated effort:** 2-3 weeks

## Approach 2: DSL Generation and Merging

### Concept

Similar to Approach 1, but composite modules generate **complete DSL fragments** that are merged/appended to the main DSL. More explicit about what gets generated.

### Architecture

```
Input YAML
    ↓
[Composite Module Pipeline]
    ↓ (generates DSL fragments)
Generated DSL Fragments
    ↓ (merge)
Merged YAML
    ↓
[Existing Module System]
    ↓
SCAD Output
```

### Implementation Flow

1. **Parse Input YAML**
2. **Execute Composite Modules** → Each generates a complete DSL fragment
3. **Merge Fragments** → Append/merge fragments into main DSL
4. **Continue Normal Pipeline**

### Example: LCD Module

**Input DSL:**
```yaml
features:
  lcd:
    - display: {...}
      mounting: {...}
```

**LCD Module Generates:**
```yaml
# Generated by composite module: lcd
features:
  cutouts:
    - face: front
      from_face_left: 50
      from_face_bottom: 30
      width: 80
      length: 40
      shape: rectangle
  
  pcb_stands:
    - x: 45
      y: 25
      height: 5
      diameter: 3
    # ... more mounts
```

**Merged Result:**
```yaml
features:
  lcd:
    - display: {...}
      mounting: {...}
  
  cutouts:
    - face: front
      from_face_left: 50
      # ... (from lcd module)
  
  pcb_stands:
    - x: 45
      y: 25
      # ... (from lcd module)
```

### Implementation Details

**Composite Module Interface:**

```go
type CompositeModule interface {
    Name() string
    Path() string
    
    // GenerateDSL creates a complete DSL fragment
    GenerateDSL(ctx context.Context, moduleData map[string]any, resolved map[string]any) (map[string]any, error)
}

// Merge strategy
func MergeDSLFragments(base map[string]any, fragments []map[string]any) map[string]any {
    result := deepCopy(base)
    
    for _, fragment := range fragments {
        result = deepMerge(result, fragment, MergeStrategyAppendArrays)
    }
    
    return result
}
```

### Pros

✅ **Explicit generation** - Clear what each composite module generates
✅ **Fragment-based** - Each module produces self-contained DSL
✅ **Easy debugging** - Can inspect generated fragments
✅ **Composable** - Multiple composite modules can generate non-conflicting fragments

### Cons

❌ **Merge complexity** - Need sophisticated YAML merging (arrays, maps, conflicts)
❌ **Conflict resolution** - What if user defines `cutouts` and module generates `cutouts`?
❌ **Ordering** - Merge order might matter

### Implementation Complexity

- **Medium-High** - Similar to Approach 1, but more explicit about fragments
- **Estimated effort:** 2-3 weeks

## Approach 3: Post-Processing Array Merging

### Concept

Composite modules run **after** regular modules, but instead of generating DSL, they **directly manipulate arrays** in the Model or SCAD output.

### Architecture

```
Input YAML
    ↓
[Existing Module System]
    ↓ (generates arrays)
Model with Arrays
    ↓
[Composite Module Pipeline]
    ↓ (modifies arrays)
Modified Model
    ↓
SCAD Output
```

### Implementation Flow

1. **Normal Pipeline** → Regular modules populate `Model` fields
2. **Composite Modules Execute** → Read their DSL, generate array entries
3. **Merge Arrays** → Append generated entries to existing arrays
4. **Emit SCAD** → Normal emission

### Example: LCD Module

**After Regular Modules:**
```go
model.Cutouts = []map[string]any{
    // User-defined cutouts
}

model.PcbStands = []map[string]any{
    // User-defined stands
}
```

**LCD Composite Module:**
```go
func (m *lcdModule) PostProcess(model *Model, lcdData map[string]any) error {
    // Generate cutout entry
    cutout := map[string]any{
        "face": "front",
        "from_face_left": 50,
        "from_face_bottom": 30,
        "width": 80,
        "length": 40,
        "shape": "rectangle",
    }
    model.Cutouts = append(model.Cutouts, cutout)
    
    // Generate pcb stand entries
    for _, pos := range mountingPositions {
        stand := map[string]any{
            "x": pos[0],
            "y": pos[1],
            "height": 5,
            "diameter": 3,
        }
        model.PcbStands = append(model.PcbStands, stand)
    }
    
    return nil
}
```

### Implementation Details

**New Hook Point:**

```go
// In pkg/yappgen/build.go or features.go
func BuildModel(resolved map[string]any, features map[string]any) (*Model, error) {
    model := &Model{}
    
    // Normal module collection
    if err := collectFeatureModules(resolved, features, model); err != nil {
        return nil, err
    }
    
    // Composite module post-processing
    if err := processCompositeModules(resolved, features, model); err != nil {
        return nil, err
    }
    
    return model, nil
}

func processCompositeModules(resolved map[string]any, features map[string]any, model *Model) error {
    featuresMap, _ := getMap(features)
    
    for key, value := range featuresMap {
        module := compositeRegistry.Get(key)
        if module == nil {
            continue
        }
        
        if err := module.PostProcess(model, value, resolved); err != nil {
            return err
        }
    }
    
    return nil
}
```

### Pros

✅ **Direct manipulation** - No DSL transformation complexity
✅ **Access to resolved values** - Can use computed values from resolution
✅ **Simple merging** - Just append to arrays
✅ **Late binding** - Runs after regular modules, can see their output

### Cons

❌ **Tight coupling** - Needs access to Model internals
❌ **Less explicit** - Harder to see what composite modules generate
❌ **Model changes** - Might need to modify Model struct
❌ **Ordering sensitive** - Must run after regular modules but before emission

### Implementation Complexity

- **Low-Medium** - Simpler than DSL transformation, but needs Model access
- **Estimated effort:** 1-2 weeks

## Approach 4: Hybrid - DSL Generation with Array Post-Processing

### Concept

Combine Approaches 1 and 3: Composite modules generate DSL entries, but these are processed **separately** and merged at the array level.

### Architecture

```
Input YAML
    ↓
[Split Pipeline]
    ├─→ [Regular Modules] ──┐
    └─→ [Composite Modules] ──┤
                              ↓
                         [Array Merge]
                              ↓
                         SCAD Output
```

### Implementation Flow

1. **Split Input** → Separate regular features from composite features
2. **Process Regular Modules** → Normal pipeline
3. **Process Composite Modules** → Generate DSL → Process through regular modules → Get arrays
4. **Merge Arrays** → Combine arrays from both pipelines
5. **Emit SCAD**

### Example

**Regular Pipeline:**
```yaml
features:
  pcb_stands:
    - x: 10
      y: 10
```
→ Generates `model.PcbStands = [...]`

**Composite Pipeline:**
```yaml
features:
  lcd:
    - display: {...}
```
→ Generates DSL → Processes through regular modules → Generates arrays
→ Generates `cutoutsArray = [...]` and `pcbStandsArray = [...]`

**Merge:**
```go
model.PcbStands = append(model.PcbStands, lcdPcbStands...)
model.Cutouts = append(model.Cutouts, lcdCutouts...)
```

### Pros

✅ **Reuses existing modules** - Composite modules generate DSL that goes through regular modules
✅ **Clear separation** - Regular vs composite processing is explicit
✅ **Leverages validation** - Generated DSL goes through normal validation

### Cons

❌ **Complex pipeline** - Need to run module system twice
❌ **Performance** - More processing overhead
❌ **State management** - Need to manage two Model instances

### Implementation Complexity

- **High** - Complex pipeline management
- **Estimated effort:** 3-4 weeks

## Approach 5: Plugin System with DSL Macros

### Concept

Composite modules are **DSL macros** that expand at parse time. More like a templating/preprocessing step.

### Architecture

```
Input YAML (with macros)
    ↓
[Macro Expansion]
    ↓
Expanded YAML
    ↓
[Existing Module System]
    ↓
SCAD Output
```

### Implementation Flow

1. **Parse YAML** → Detect macro syntax (e.g., `!lcd {...}`)
2. **Expand Macros** → Call composite modules to expand macros
3. **Continue Normal Pipeline**

### Example: LCD Module

**Input DSL:**
```yaml
features:
  cutouts:
    - !lcd
      display:
        face: front
        position: [50, 30]
        size: [80, 40]
      mounting:
        type: pcb_stands
        positions: [[45, 25], [45, 55], [105, 25], [105, 55]]
```

**Expanded:**
```yaml
features:
  cutouts:
    - face: front
      from_face_left: 50
      from_face_bottom: 30
      width: 80
      length: 40
      shape: rectangle
  
  pcb_stands:
    - x: 45
      y: 25
      height: 5
      diameter: 3
    # ... more mounts
```

### Pros

✅ **Familiar pattern** - Macros are common in DSLs
✅ **Explicit expansion** - Clear where macros are used
✅ **Early expansion** - Happens before any processing

### Cons

❌ **Custom YAML syntax** - Need custom YAML tags (`!lcd`)
❌ **Parser complexity** - Need to handle custom tags
❌ **Less flexible** - Macros must expand inline

### Implementation Complexity

- **Medium-High** - Need custom YAML tag handling
- **Estimated effort:** 2-3 weeks

## Comparison Matrix

| Approach | Complexity | Separation | Flexibility | Maintainability | Performance |
|----------|-----------|------------|------------|----------------|-------------|
| 1. Pre-Processing DSL Transform | Medium | High | High | High | Medium |
| 2. DSL Generation & Merge | Medium-High | High | High | High | Medium |
| 3. Post-Processing Array Merge | Low-Medium | Medium | Medium | Medium | High |
| 4. Hybrid | High | Medium | High | Medium | Low |
| 5. DSL Macros | Medium-High | High | Medium | High | High |

## Recommendation

**Approach 1: Pre-Processing DSL Transformation** is recommended because:

1. ✅ **Clean separation** - Composite modules are completely separate from regular modules
2. ✅ **No changes to existing code** - Zero impact on current module system
3. ✅ **Easy to understand** - DSL transformation is explicit and debuggable
4. ✅ **Flexible** - Can generate any DSL structure
5. ✅ **Testable** - Can test transformations independently
6. ✅ **User-friendly** - Users can inspect transformed YAML if needed

### Implementation Plan for Approach 1

1. **Create `pkg/composite/` package**
   - `module.go` - CompositeModule interface
   - `registry.go` - Registry for composite modules
   - `pipeline.go` - DSL transformation pipeline
   - `merge.go` - YAML merging utilities

2. **Integrate into resolver pipeline**

3. **Create first composite module: LCD**
   - `pkg/composite/modules/lcd/`
   - Schema definition
   - Transform logic

4. **Testing**

## Open Questions

1. **Conflict Resolution**: What happens if composite module generates `cutouts` entry that conflicts with user-defined `cutouts`?
   - Option A: Append (both exist)
   - Option B: Replace (composite overwrites)
   - Option C: Error (user must resolve)
   - Option D: Namespace (composite entries marked/tagged)

2. **Ordering**: Should composite modules run in a specific order?
   - Option A: Registration order
   - Option B: Dependency order (if modules depend on each other)
   - Option C: Alphabetical

3. **Validation**: When should composite-generated DSL be validated?
   - Option A: Before merging (validate generated DSL)
   - Option B: After merging (validate merged DSL)
   - Option C: Both

4. **Error Handling**: How to handle errors from composite modules?
   - Option A: Fail fast (stop processing)
   - Option B: Collect errors, report all at once
   - Option C: Skip composite module, continue with rest

5. **Debugging**: How to help users debug composite module transformations?
   - Option A: Flag to output transformed YAML
   - Option B: Logging of transformations
   - Option C: Dry-run mode

6. **Performance**: Should composite modules be cached if input doesn't change?
   - Option A: Yes, cache transformations
   - Option B: No, always regenerate
