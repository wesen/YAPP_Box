## Goal

Reproduce the workflow described in `playbook/02-yapp-documentation-study-playbook.md`: locate the scraped YAPP docs, query `yapp_analysis.db`, and correlate the guidance with real SCAD examples. Use this whenever you need an up-to-date local copy of the documentation or want to verify GitBook content before hacking on the DSL/generator.

## Locations (Same as the original playbook)

- **Docs workspace**: `ttmp/YAPP-DOCS-001-fix-yappgenerator-documentation-issues-and-update-gitbook`
  - `analysis/query_db.py`, `analysis/yapp_analysis.db`, `analysis/scrape_gitbook.py`
  - `reference/` and `fixes/` hold curated notes and GitBook patch files
- **Examples**: `examples/` (cutouts, light tubes, shapes, etc.)
- **Case study**: `ttmp/PICO-TEMP-001-*/` for a real enclosure

- `python3` with `tabulate` (run `python3 -m pip install --user tabulate` if missing).
- `sqlite3` CLI for ad-hoc queries.
- OpenSCAD (only required when validating example fixes).
- Repository checked out at repo root: `/home/manuel/code/others/YAPP_Box`.

All paths below are relative to that root.

## 1. Familiarize Yourself with the Workspace

```bash
cd ttmp/YAPP-DOCS-001-fix-yappgenerator-documentation-issues-and-update-gitbook
bat README.md
ls design reference playbooks fixes
```

Key files:
- `tasks.md` tracks outstanding GitBook corrections (defaults reference, GitBook re-scrape, analyzer rerun).
- `fixes/` contains Markdown patches already staged for GitBook maintainers.
- `analysis/` holds scripts and **`yapp_analysis.db`**, the canonical issue tracker for docs/examples/API changes.

## 2. Inspect the Analysis Database

Enter the analysis folder and use the helper script:

```bash
cd analysis
./query_db.py summary
```

As of the latest run this reports:
- **100 commits** analyzed, **43** with API changes.
- **9** tracked API changes (no breaking changes).
- **10** open documentation issues (2 critical, 5 high, 3 medium).
- **122** open example issues (generated by the automated analyzer).
- **2** fix recommendations queued.

List doc issues with severity buckets:

```bash
./query_db.py docs               # all open issues
./query_db.py docs critical      # just the blockers
```

For deeper dives or custom filters, use SQL:

```bash
sqlite3 yapp_analysis.db "SELECT page_name, description FROM doc_issues WHERE severity='high'"
```

Document the query output directly in your fix notes so reviewers can trace every GitBook change back to a DB row.

## 3. Map Issues to Fix Tasks

Cross-reference DB findings with `../tasks.md`:

1. Highlight **critical** rows first (Version mismatch, Include order). Confirm tasks exist; if not, add them.
2. For **high** severity rows (yappCenter usage, parameter notation, PCB stands order, Push Buttons/Light Tubes examples) verify whether fixes already landed in `fixes/`.
3. Use `./query_db.py query "..."` to pull affected URLs or code blocks when preparing GitBook PRs. Example:

```bash
./query_db.py query "
SELECT p.title, p.url, c.issue_description
FROM gitbook_pages p
JOIN gitbook_code_examples c ON c.page_id = p.id
WHERE c.issue_description LIKE '%yappCenter%'
"
```

Save the output under `fixes/NN-page-name.md` so reviewers see the before/after context in one place.

## 4. Validate Examples and Examples Tables

Many issues stem from stale examples. Use the analyzer to reproduce warnings locally:

```bash
python3 analyze_examples.py --examples-dir ../../examples --treat-warnings-as-errors
```

For targeted checks (e.g., Push Buttons):

```bash
sqlite3 yapp_analysis.db "
SELECT p.title, c.code_block
FROM gitbook_pages p
JOIN gitbook_code_examples c ON c.page_id = p.id
WHERE p.title='Push Buttons' AND c.issue_description LIKE '%yappCenter%'
"
```

After patching the `.scad` or GitBook content, re-run `analyze_examples.py` and confirm the warning disappears before closing the row in `doc_issues`.

## 5. Close the Loop in the Database

When a documentation fix is merged (either in GitBook or this repo), update the DB so future audits stay signal-driven:

```bash
sqlite3 yapp_analysis.db "
UPDATE doc_issues
SET status='resolved', updated_at=CURRENT_TIMESTAMP
WHERE page_name='Include Order';
"
```

Then regenerate the summary to confirm counts drop as expected:

```bash
./query_db.py summary
```

(If you rely on automation to repopulate the DB—e.g., via `populate_doc_issues.py`—commit the SQL changes or the updated script so the status change persists.)

## 6. Export Fix Reports

When you need a shareable checklist for PMs or GitBook maintainers, generate a CSV/Markdown table straight from the DB:

```bash
./query_db.py query "
SELECT page_name AS page,
       severity,
       suggested_fix AS fix,
       status
FROM doc_issues
WHERE status='open'
ORDER BY severity;
" > open_doc_issues.md
```

Attach this to ticket updates or include in the `fixes/` subfolder alongside the corresponding patch.

## 7. Recommended Flow (mirrors playbook/02)

1. **Sync tickets** → `git pull`, open `ttmp/YAPP-DOCS-001/.../tasks.md`.
2. **Query docs DB** → `./query_db.py readme`, `... docs critical`, `... api v3.3.8`.
3. **Read target page** → `sqlite3 yapp_analysis.db "SELECT content FROM gitbook_pages WHERE title='Cutouts';"`.
4. **Inspect examples** → render relevant demos from `examples/` or the case study.
5. **Record findings** → add notes to `fixes/NN-page.md` or update GitBook directly.
6. **Update metadata** → close issues in `doc_issues`, tick `tasks.md`, regenerate summaries.

Following this loop keeps your local YAPP documentation snapshot aligned with the repo and mirrors the “YAPP Documentation Study Playbook” process, but now you can reach it directly via the CLI help system.
